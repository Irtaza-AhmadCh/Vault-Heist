Vault Heist: The Living Vault

Complete Technical Manual: System Architecture, File Hierarchy, Header & Implementation Roles, and JSON Specification
C++17 | SFML 2.6.2 | MVC Pattern | Data Structures & Algorithms
Project Summary
Vault Heist: The Living Vault is a high-performance educational gamified experience designed to teach fundamental and advanced hierarchical data structures. The player takes the role of an elite cyber-infiltrator navigating an organic bio-neural vault. The game features 4 distinct Acts: Act 1: The Blueprint Wing (General Binary Trees), Act 2: The Logic Core (Binary Search Trees), Act 3: The Balancing Vault (Self-Balancing AVL Trees), and Act 4: The Priority Core (Binary Max Heaps). Progression requires executing exact algorithmic invariants while staying within strict alarm step budgets.

1. Architectural Pattern & Arrangement

The project adheres strictly to the Model-View-Controller (MVC) architectural pattern. This design guarantees decoupling between underlying tree nodes, gameplay progression rules, and graphical rendering pipelines:

  • Model / Logic (game/logic/): Encapsulates pure data structure algorithms. Implements raw pointer-based dynamic trees (Binary Tree, BST, AVL, Max Heap), node rotation formulas, predecessor/successor replacements, and decoupled operation logging. It maintains zero dependencies on SFML or GUI code.
  • Controller (game/controller/ & game/scoring/): Manages game state machines, level parameters, player action validation (verifying whether clicked nodes match binary search or tree traversal paths), scoring, star calculation, and undo snapshots.
  • View (game/view/): Owns SFML window rendering, layout engines that compute hierarchical 2D node coordinates, procedural bioluminescent node depictions, glowing edge tendrils, animations, buttons, input fields, and HUD alarm bars.

3. Role of JSON Files in the Architecture

The project includes a suite of structured JSON files under the levels/ folder (e.g., campaign_levels.json, act1_levels.json, act2_levels.json, act3_levels.json, and act4_levels.json). These files play three pivotal architectural roles:

  1. Data-Driven Level Design (Separation of Content and Code): Instead of hardcoding puzzles, target numbers, and dialogues inside C++ source code, level definitions are stored as declarative data. Game designers can tweak balance, optimal step thresholds, and objectives without recompiling the project.
  2. Standardized Level Schema: Every level entry conforms to a structured specification:
    • act & level: Numeric identifiers routing to the campaign map.
    • title & objective: Explanatory text rendered directly in the bottom HUD banner.
    • structureType: Tells the engine which data structure to initialize ("tree", "bst", "avl", "heap").
    • requiredAction: Informs UniversalActController which invariant to test (e.g., "search", "inorder", "reconstruct", "range_query", "delete", "rotate").
    • targetValue: The algorithmic target key to locate, balance, or remove.
    • optimalSteps: The baseline par value used by ScoreSystem to award 1, 2, or 3 stars based on alarm efficiency.
    • hint: Contextual algorithmic hints displayed when the player requests assistance.
  3. Extensibility & Custom Campaigns: New levels, custom user heists, or tournament scenarios can be introduced simply by appending entries to the JSON file.
Architectural Flow Summary
When a user clicks on a node on the screen:
  1. GameScreen captures the SFML click coordinates and queries TreeLayout to find the selected node key.
  2. GameScreen invokes LevelManager::notifyAction("search", selectedKey).
  3. LevelManager passes the request to UniversalActController, which checks the move against the data structure invariants in game/logic/.
  4. If correct, the alarm meter increments normally; if incorrect, a penalty is recorded.
  5. ScoreSystem recalculates remaining alarm budget. Upon target completion, victory is triggered and SaveManager writes updated stars to disk.
