VAULT HEIST: THE LIVING VAULT TWO-PERSON PARALLEL DEVELOPMENT ROADMAP

Purpose This roadmap divides the project between two developers so both
members can work at the same time. It defines responsibilities,
development phases, integration points, testing duties, and a shared Git
workflow. The goal is to build separate modules independently and
combine them regularly, rather than waiting until the end to merge the
entire project.

The plan is based on the project elements discussed: Binary Tree, Binary
Search Tree (BST), AVL Tree, Max Heap, visualization, animation,
campaign and level systems, testing, and benchmarking. Exact
requirements, signatures, scoring formulas, and level rules must be
checked against the original assignment specification. Where those
details are not available here, the team should agree on them before
implementation rather than assume them.

1.  TEAM STRUCTURE AND OWNERSHIP

MEMBER A: BINARY TREE, BST, TREE VISUALIZATION, ACTS 1 AND 2

Member A is responsible for: - BinaryTree node and basic tree
implementation. - Preorder, inorder, postorder, and level-order
traversals. - Tree construction or reconstruction operations required by
the assignment. - Tree height and diameter. - Lowest Common Ancestor
(LCA) and mirror/invert operations where required. - Binary Search Tree
insertion and searching. - BST deletion, including leaf, one-child, and
two-child cases. - BST minimum and maximum. - BST successor and
predecessor. - BST range query and validation. - General tree layout and
rendering. - Tree node and edge visualization. - Traversal highlighting
and animations. - BST search, insertion, and deletion visualization. -
Gameplay and level logic assigned to Acts 1 and 2. - BinaryTree and BST
unit tests. - Tree-related documentation and benchmarking.

MEMBER B: AVL TREE, MAX HEAP, ADVANCED VISUALIZATION, ACTS 3 AND 4

Member B is responsible for: - AVL node structure and metadata. - AVL
insertion and deletion. - AVL balance factor and height updates. - LL,
RR, LR, and RL rotations. - AVL validation. - subtreeSize maintenance if
required. - kth and rank operations if required. - MaxHeap
implementation. - buildMaxHeap, siftUp, and siftDown. - extractMax and
Heap Sort. - MaxHeap validity checks. - AVL rotation visualization. -
Balance factor and height metadata display. - Heap tree visualization. -
Heap array visualization and synchronization between the two views. -
Animation controller or queue, subject to the shared ownership
agreement. - Gameplay and level logic assigned to Acts 3 and 4. - AVL
and MaxHeap unit tests. - AVL/Heap documentation and benchmarking.

SHARED RESPONSIBILITIES

Both members must agree on: - Programming language, compiler, GUI
framework, and build configuration. - Folder structure, naming
conventions, and public interfaces. - Event format and communication
between the model and visual layer. - Main application architecture. -
Campaign and level integration. - Score system and alarm meter. - Event
log, undo, and replay. - Save and load. - Sandbox or endless mode, if
required. - Final application testing, report preparation, and
demonstration.

For every shared module, choose one primary owner before implementation.
The other member should review and test it. Do not let both members edit
the same shared files independently without coordination.

2.  DEVELOPMENT PRINCIPLES

The team should follow these principles throughout the project:

1.  Interface first: agree on class names, method names, parameters,
    return values, and data ownership before implementing dependent
    modules.

2.  Independent modules: each member owns separate source files and
    tests wherever possible.

3.  Mock implementations: if a dependency is not ready, use a temporary
    local mock or test fixture so work can continue.

4.  Continuous integration: merge small, working changes after each
    milestone.

5.  Model and GUI separation: data structures should not directly draw
    graphics or manipulate GUI widgets.

6.  Test every module: each structure should have unit tests before it
    is connected to the complete application.

7.  Shared understanding: both members should understand the overall
    architecture and be ready to explain the complete project.

8.  PHASE 0 — ARCHITECTURE AGREEMENT

Estimated duration: half a day to one day. Working arrangement: both
members work together.

Objective: Create a common technical foundation so the modules can be
developed independently and connected later without major interface
changes.

Tasks for both members: 1. Confirm the programming language, compiler
version, GUI framework, and build configuration required by the
assignment. 2. Agree on the repository and folder structure. 3. Define
public interfaces for BinaryTree, BST, AVLTree, and MaxHeap. 4. Agree on
how data-structure operations report changes to the visual layer. 5.
Define the boundary between model logic, event logging, animation
control, and rendering. 6. Agree on error handling and memory ownership.
7. Decide whether operations mutate structures in place or return
results. 8. Create a minimal buildable application shell and a test
target.

Illustrative interface sketch:

class BinaryTree { public: void preorder(); void inorder(); void
postorder(); void levelOrder(); int height(); int diameter(); };

class BST { public: void insert(int key); bool search(int key); void
deleteNode(int key); };

class AVLTree { public: void insert(int key); void deleteNode(int key);
int kth(int k); int rank(int key); };

class MaxHeap { public: void buildMaxHeap(); void siftUp(int index);
void siftDown(int index); int extractMax(); void heapSort(); };

These signatures are examples only. The team must confirm exact
parameters, return types, error behaviour, and naming conventions before
coding.

Phase 0 deliverables: - Agreed public interfaces or header files. -
Shared event specification. - Agreed model/event/animation/rendering
architecture. - Repository with main and feature branches. - Build
instructions. - Minimal project shell that compiles. - Written ownership
list for source files.

Exit condition: Both members can build the project shell and explain how
a data-structure operation reaches the visual layer.

SHARED VISUALIZATION CONTRACT

A data-structure operation should not directly draw pixels or manipulate
GUI widgets. The model should report what changed. The event or
animation layer should interpret the change. The renderer should display
it.

This separation allows data structures to be tested without starting the
GUI and helps prevent visual code from changing the underlying algorithm
behaviour.

9.  GIT WORKFLOW AND MERGING RULES

Use one shared repository with a protected main branch and separate
feature branches.

Suggested branches: - main - feature/member-a-binary-tree-bst -
feature/member-b-avl-heap-visuals

DAILY WORKFLOW FOR EACH MEMBER

1.  Pull the latest shared branch before starting work.
2.  Work in the files assigned to your module.
3.  Build and run the module’s tests locally.
4.  Commit small, understandable changes.
5.  Push the branch regularly.
6.  Open a pull request describing the files changed, behaviour added,
    and tests run.
7.  Ask the other member to review interface and integration impact.
8.  Merge only after the agreed checks pass.

RULES TO PREVENT MERGE CONFLICTS

-   Do not both edit the same file independently.
-   Put shared declarations in agreed headers or interface files.
-   Do not duplicate class definitions.
-   Keep GUI code out of data-structure implementation files.
-   Do not rename public methods without informing the other member.
-   Merge small pull requests frequently.
-   Assign one owner to each shared module.
-   Communicate interface changes before implementing them.

SUGGESTED FILE OWNERSHIP

-   structures/binary_tree/: Member A.
-   structures/bst/: Member A.
-   structures/avl/: Member B.
-   structures/heap/: Member B.
-   visualization/tree/: Member A.
-   visualization/heap/: Member B.
-   visualization/animation/: Member B, coordinated with the shared
    event contract.
-   game/levels/act1-2/: Member A.
-   game/levels/act3-4/: Member B.
-   shared core, main application, and build files: assign a named owner
    together.

A pull request is ready to merge only when it builds, tests pass, the
interface is documented, and the other member understands its impact.

10. MASTER TIMELINE AND INTEGRATION GATES

Phase 0 — Architecture agreement: Estimated duration: 0.5 to 1 day.
Member A: agree on APIs and events. Member B: agree on APIs and events.
Integration gate: buildable application shell and documented contracts.

Phase 1 — Core structures: Estimated duration: 3 to 5 days. Member A:
BinaryTree foundation. Member B: MaxHeap foundation and AVL groundwork.
Integration gate: both modules compile and pass initial tests.

Phase 2 — Advanced structures: Estimated duration: 3 to 5 days. Member
A: BST implementation. Member B: AVL completion and Heap verification.
Integration gate: structure invariants and unit tests pass.

Phase 3 — GUI and visualization: Estimated duration: 4 to 6 days. Member
A: tree and BST visualization. Member B: AVL and Heap visualization and
animation infrastructure. Integration gate: both visual modules connect
to the same application.

Phase 4 — Game integration: Estimated duration: 3 to 4 days. Member A:
Acts 1 and 2 and assigned shared tasks. Member B: Acts 3 and 4 and
assigned shared tasks. Integration gate: campaign flow and shared game
systems work.

Phase 5 — Testing and submission: Estimated duration: 2 to 3 days.
Member A: tree tests, documentation, and benchmarking. Member B:
AVL/Heap tests, documentation, and benchmarking. Integration gate: clean
build, complete tests, and demonstration readiness.

Estimated total duration: approximately 16 to 24 days.

These estimates assume both members work consistently and the scope does
not change. They are planning estimates, not fixed deadlines.

Do not move to the next phase just because the estimated number of days
has passed. Move forward when the phase’s exit condition is met. If one
module is delayed, the other member should continue using the agreed
interface and a mock or stub instead of becoming blocked.

WEEKLY COORDINATION MEETING

Hold a short meeting of approximately 15 to 25 minutes. Discuss: - What
was completed and merged? - What is currently blocked? - What interface
or decision is missing? - Does either member need to edit a shared
file? - What will each member deliver before the next meeting? - Which
tests and integration gate must pass next?

11. RISKS AND SAFEGUARDS

Risk: Member A’s BST implementation delays Member B’s AVL work.
Safeguard: Member B develops AVL against the agreed interface and local
test fixtures.

Risk: Members make different assumptions about node fields or ownership.
Safeguard: Agree on the node and API contract in Phase 0 and review
changes before merging.

Risk: GUI and model code become tightly coupled. Safeguard: Keep model
operations independent of rendering and communicate through events.

Risk: Both members edit the same shared file. Safeguard: Assign one
owner per shared module and use pull requests.

Risk: Integration is postponed until the end. Safeguard: Use the
integration milestones and merge continuously.

Risk: Tests cover only normal inputs. Safeguard: Include empty,
single-node, duplicate, skewed, and boundary cases where relevant.

Risk: Only one member understands the project. Safeguard: Conduct short
code walkthroughs and prepare jointly for the demonstration.

12. TEAM AGREEMENT

Both members agree to: - Work in parallel within the agreed module
boundaries. - Keep public interfaces stable and communicate changes. -
Avoid uncoordinated edits to shared files. - Build and test modules
before merging. - Integrate after each milestone. - Help review each
other’s code. - Understand the complete project, not only their own
modules. - Prepare together for the final demonstration and viva.
